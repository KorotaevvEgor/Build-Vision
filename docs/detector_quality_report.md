# Качество детектора на val-выборке (20 снимков)

Дата замера: результаты baseline-прогона `20260914-230535-val-960px-val-eval`
(YOLO-World v2 small, CPU, imgsz=960, conf=0.25, class-агностичный NMS,
словарь `data/config/vocabulary.yaml`). Разметка — ручной визуальный аудит
всех 20 снимков `val` (не `dev`, не `holdout`), выполненный после фиксации
модели и порогов, чтобы не подгонять настройки под контрольную выборку.

## Методика оценки

Оценка сделана **на уровне присутствия класса на снимке** («класс виден
хотя бы одной рамкой» — да/нет), а не через IoU с эталонными рамками.
Это осознанное упрощение по двум причинам:

1. Именно так результат детектора используется в ядре сопоставления
   (`matching.py`): правила проверяют *присутствие* требуемого класса
   в зоне, а не точную локализацию отдельных объектов.
2. Точная bbox-разметка каждого объекта на 20 плотных строительных
   панорамах (местами 30–60 объектов на кадр — буровые установки,
   краны, техника вперемешку) потребовала бы кратно больше времени, чем
   есть в рамках хакатона; result бы не изменил выводов ниже.

Это **не полноценный mAP** и не заменяет его — для этого нужна
инструментальная bbox-разметка, вынесенная в раздел «Дальнейшая работа».

## Результаты по ключевым классам

### Экскаватор
* Присутствует по факту (GT): 18 из 20 снимков.
* Верно отмечен моделью (TP): 14.
* Полностью пропущен — не назван «Экскаватор» ни одной рамкой,
  везде подменён «Кран-манипулятором» (FN): 4 снимка
  (Screenshot_25, 46, 95, 97).
* Ложно назван «Экскаватор» на объекте, который им не является
  (буровая установка, FP): 1 снимок (Screenshot_9).
* **Precision ≈ 0.93, Recall ≈ 0.78.**

Точность высокая: если модель говорит «экскаватор», это почти всегда
правда. Проблема — в полноте: почти четверть реальных экскаваторов
целиком «теряется» под чужим классом.

### Самосвал
* Присутствует по факту (GT): 1 из 20 снимков (Screenshot_86, синий
  самосвал с поднимающимся кузовом).
* Модель предсказывала класс «Самосвал» **в каждом из 20 снимков**,
  в основном на трубах, панелях перекрытий, морских контейнерах,
  штабелях мешков и прочих прямоугольных объектах фона.
* **Precision ≈ 0.05, Recall = 1.0** (единственный реальный самосвал
  найден, но ценой примерно 19 ложных срабатывания на снимок в среднем).

Это самая серьёзная находка отчёта: precision промпта «dump truck»
на этом датасете практически неприемлема для продакшена без
дополнительной калибровки. Высокий recall здесь не показатель качества:
он тривиален при почти повсеместных ложных срабатываниях.

### Автобетоносмеситель
* Присутствует по факту (GT): 2 из 20 снимков (Screenshot_41, 97 —
  видны бетоновозы с барабаном).
* Ни разу не назван моделью правильным классом (0/2, оба раза объект
  либо не размечен вовсе, либо перекрыт рамкой другого класса).
* Слишком мало примеров для точных Precision/Recall, но направление
  ясное: класс либо отсутствует в датасете, либо систематически
  пропускается — требует отдельного внимания при расширении словаря/промптов.

### Каток — новое условие путаницы
* Screenshot_60: реальный дорожный каток уверенно (0.50) назван
  «Кран-манипулятор». До этой разметки пара (каток, кран-манипулятор)
  не была в списке `confusable_class_pairs` — добавлена по итогам
  аудита в `data/config/equipment_rules.yaml`.

## Что это значит для продукта

* Механизм неоднозначности (`detector.py`, confusable-пары) корректно
  закрывает случаи «экскаватор/каток случайно назван краном-манипулятором»
  — для них система будет честно показывать «Недостаточно данных»
  вместо уверенного, но неверного ответа.
* Он **не закрывает** проблему самосвала: это не путаница с другим
  членом таксономии, а систематические ложные срабатывания на фоне.
  Механизм confusable-пар для этого не подходит. Рекомендация на
  дальнейшую работу: поднять порог confidence конкретно для класса
  dump_truck, уточнить промпт (например, добавить признак кузова
  самосвала), либо явно предупреждать в интерфейсе, что предупреждения
  по самосвалу требуют повышенной ручной проверки до дополнительной
  калибровки.
* Автобетоносмеситель как класс в этой версии не готов к автоматической
  проверке — при использовании в демонстрации полагаться на него не
  стоит без ручного подтверждения кадра.

## Ограничения этой оценки

* Основана на 20 снимках одной val-части; она не заменяет проверку на
  holdout (20 снимков), который сознательно не использовался, чтобы
  сохранить его независимость для финальной проверки.
* Presence-уровень не показывает, сколько рамок на кадр верны/лишни —
  только сам факт «класс найден/не найден».
* Разметка сделана одним человеком (агентом) визуально, без второго
  независимого разметчика — возможны отдельные спорные случаи на очень
  мелких/дальних объектах.
