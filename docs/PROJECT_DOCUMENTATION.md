# BuildVision - документация решения

Версия 1.2 · 20 октября 2026 · Состояние исходного кода, без заявления о развёртывании.

Назначение: техническое описание, воспроизводимая установка, руководство пользователя и сценарии проверки. Публичная версия не содержит снимков заказчика, персональных данных и значений секретов. PDF: `frontend/public/BuildVision-documentation.pdf`.

## 1. Назначение и границы поставки

BuildVision связывает снимок строительной площадки с камерой, рабочим участком, датой и требованиями календарного плана. Результат - проверяемое сравнение количества видимой техники с заданным ресурсным требованием. Система помогает инженеру организовать проверку; сама по себе не удостоверяет простой, отсутствие техники на всей площадке или объём выполненных работ.

Реализованы проекты и роли, камеры и архив, полигоны рабочих участков, количественные правила, журнал отклонений, независимые визуальные доказательства, критический путь, ввод подтверждённых физических объёмов и сценарные сроки, погодные риски, коррекции распознавания и классификатор-корректор. Веб-интерфейс использует общий API с Android-обёрткой Capacitor.

| Возможность | Текущая поставка | Граница |
|---|---|---|
| Vision | YOLO-World, словарь, рамки, зональный отбор | Качество проверяется на конкретной выборке; уверенность модели не является гарантией |
| Learning | Коррекции инженера, CLIP-признаки, кандидат и ручная публикация | Текущий обучающий контур связан с legacy-данными; не заявляется многопроектное обучение |
| Weather | Open-Meteo, почасовые риски на 72 часа | Внешний источник, не доказательство фактической остановки |
| Planning | Детерминированные Python-правила и расчёт сети | Локальная Qwen и её инструменты остаются целевой архитектурой |
| Отклонения | Доказательства, статусы и журнал решений | Визуальное повторение и инженерное подтверждение различаются |
| Сроки | Замер объёмов, оценка ответственного, сценарий темпа | Без замеров показан плановый ориентир |

Целевые доработки: идентичность машин между камерами, калиброванная мировая геометрия, локальный координатор Qwen, проверенная промышленная выборка, фоновая push-доставка и полностью изолированный сетевой контур. Наличие схемы этих модулей не означает их интеграцию.

## 2. Архитектура и модель данных

Веб-клиент React / TypeScript обращается к FastAPI. Сервер выполняет детекцию и расчёт правил; Django ORM связывает API с PostgreSQL и административной панелью. Docker Compose содержит db, app и admin. Сервис app раздаёт собранный веб-клиент и API с одного адреса; nginx и HTTPS настраиваются на границе установки.

Путь обработки: загрузка -> проверка проекта и времени -> детекции -> пространственный отбор -> требования активных работ -> количественное сравнение -> сохранение наблюдения -> доказательства и задача инженеру. Необязательное языковое обогащение отделено от основного результата.

| Сущность | Назначение и сохранённое основание |
|---|---|
| ConstructionSite / ProjectMembership | Объект и доступ участника; администратор управляет проектами |
| Zone / Camera / FrameZone | Площадочная зона, камера, полигон кадра с назначением и связью с работой |
| Stage / StageRule / StageRequiredItem | Даты, иерархия, FS-связи, обязательные количества и допустимые классы |
| Observation / Detection | Файл, SHA-256, дата, точное время съёмки при наличии, рамки и классы |
| StageEvaluationRecord | Исторические план/факт, объяснение и methodology_snapshot |
| Deviation / DeviationEvidence | Задача, состояния, независимость наблюдения, серия и причины исключения |
| Correction / ModelVersion | Исправление инженера, обучающий кандидат и версия корректора |

Методический снимок сохраняет версию алгоритма work-zones-v2, параметры требования, геометрию зон, посчитанные и исключённые детекции, причины исключения и SHA-256 отпечаток правила. Отпечаток позволяет проверить сопоставимость наблюдений; это не цифровая подпись и не защита от администратора БД.

При повторном анализе предыдущие структурированные детекции и оценки архивируются в Observation.analysis_history перед заменой текущей версии. Это история результатов, а не неизменяемый внешний архив. Резервировать необходимо и БД, и исходные изображения, и модели.

## 3. Модель, классы, данные и качество

Базовый детектор - YOLO-World v2 small, открытый словарь на английских текстовых промптах. В конфигурации по умолчанию: yolov8s-worldv2.pt, размер изображения 960, общий порог 0.25. Значения SK_MODEL_WEIGHTS, SK_IMGSZ и SK_CONF переопределяют запуск. Промпты не выбираются по ожидаемому этапу: иначе система перестала бы замечать неожиданную технику.

| Ключ | Класс | Ключ | Класс |
|---|---|---|---|
| dump_truck | Самосвал | excavator | Экскаватор |
| road_roller | Каток | crane_manipulator | Кран-манипулятор |
| concrete_mixer | Автобетоносмеситель | bulldozer | Бульдозер |
| truck | Грузовик | mobile_crane | Автокран |

Дополнительные нерелевантные классы car, bus, person помогают не приписывать каждый объект восьми целевым классам. Канонический словарь хранится в data/config/vocabulary.yaml и в БД после сида. Изменения словаря и порогов требуют повторной проверки качества.

Методика проверки и границы интерпретации результатов описаны в docs/VALIDATION.md. Проверка присутствия класса не измеряет точность рамок и не равна mAP или точности количества.

Исследовательская проверка не даёт оснований объявлять промышленную точность. Малое число сцен, один разметчик, недостаток примеров отдельных классов и неподтверждённая независимость камер ограничивают выводы. Новые проценты качества здесь не заявляются; решение об активации порогов следует брать из актуального отчёта, а не из презентации. Текущий кандидат калибровки отклонён по проверочной части; новые пороги не активированы, улучшение точности не заявляется.

Обучение Learning корректирует класс по CLIP-признакам на исправлениях инженера. Это дополнительный классификатор, не дообучение всех весов YOLO. Нужны независимые объекты и камеры для контроля утечки, bbox-разметка для локализации, оценка количества и ложных тревог для продуктового сценария. Неоднозначные объекты требуют ручной проверки.

## 4. Алгоритм количественного сопоставления

Работа выбирается по площадочной зоне и подтверждённой дате снимка: start_date <= observed_date <= end_date. Определённая машина на снимке не доказывает, что соответствующая работа началась. Нет даты, нормы или достаточного основания - результат «Недостаточно данных».

В рабочий факт включаются уверенные релевантные детекции подходящего рабочего полигона. Стоянка, въезд, опасный или неконтролируемый участок, зона другой работы и объекты вне разметки не увеличивают количество рабочего ресурса. На карточке остаются видимый состав и причины исключения. При отсутствии проверяемого рабочего участка нельзя выдавать охват всего кадра за проверку полного ресурса работы.

Для класса k:

```text
N_fact(k) = количество пригодных детекций k в рабочем участке
shortfall(k) = max(0, N_plan(k) - N_fact(k))
satisfied(k) = N_fact(k) >= N_plan(k)
```

Пример: план 6 самосвалов, в рабочем полигоне видно 2, ещё 3 находятся на стоянке. Рабочий факт - 2, визуальный дефицит - 4; 3 машины на стоянке показываются как исключённые. Это не утверждение, что на всём объекте есть только 2 самосвала.

Для одновременно активных работ разрешённый набор объединяется, чтобы техника параллельной операции не считалась посторонней. Но одна машина общего участка не может автоматически обеспечить несколько работ: при общей потребности без разделения назначения возвращается неопределённость распределения. Выход - разметить отдельные участки или уточнить назначение ресурса.

Система выдаёт три исхода: «Отклонений не выявлено», «Возможное отклонение», «Недостаточно данных». Первый означает соответствие наблюдаемого ресурса доступному правилу; он не подтверждает завершение этапа, безопасность всей площадки или правильность исходной нормы. Нормы из демонстрационной конфигурации необходимо согласовать с ППР и технологическими картами.

## 5. Доказательства и жизненный цикл отклонения

Одна пригодная фиксация создаёт основание для проверки. Отдельная запись DeviationEvidence показывает, является ли кадр независимым и сопоставимым. Старые счётчики без таких записей помечаются legacy_unverified и не превращаются задним числом в доказанную серию.

| Проверка | Для независимого подтверждения |
|---|---|
| Источник | Камера определена; файл имеет новую SHA-256 |
| Время | Дата подтверждена и captured_at задан с часовым поясом |
| Работа | Есть пригодная оценка работы и проверенный рабочий участок |
| Сопоставимость | Та же камера и неизменный отпечаток правила / геометрии |
| Последовательность | Время позже предыдущего, интервал соответствует профилю |
| Исход | Повторное расхождение или пригодное контрольное соответствие |

Начальный профиль в коде: не менее 2 кадров, минимальный интервал 600 секунд, максимальный разрыв последовательной серии 5400 секунд. Параметры SK_PROOF_MIN_FRAMES, SK_PROOF_MIN_INTERVAL_SECONDS и SK_PROOF_MAX_INTERVAL_SECONDS настраиваются окружением. Это инженерный профиль подтверждения, а не строительная норма и не доказанный технологический простой.

Повтор файла и повторная обработка не увеличивают независимое подтверждение. Кадр без точного подтверждённого времени может оставаться полезным историческим наблюдением, но не подтверждает временную серию. Изменение правила, камеры или геометрии требует отдельной проверки сопоставимости. Непригодное наблюдение не доказывает ни нарушение, ни устранение.

Один «чистый» кадр не закрывает задачу автоматически: он показывает, что расхождение на этом контрольном наблюдении не воспроизвелось. Визуальная серия, инженерное подтверждение обстоятельств, устранение и подтверждение устранения - разные характеристики. Решение пользователя и комментарий остаются в журнале. Кнопка «Подтвердить обстоятельства» вызывает проектный POST /deviations/{id}/review и требует комментарий. Отдельная запись engineering_review сохраняет автора, время и основание; она не меняет визуальную доказательность или статус задачи. Для переходов resolved / confirmed / dismissed также требуется комментарий.

Камеры не объединяются в глобальный точный счётчик машин. Идентификация одного объекта в пересекающихся обзорах - целевой модуль; текущие независимые наблюдения разных камер не следует суммировать как новые машины или последовательные подтверждения.

## 6. Сценарные сроки и физический прогресс

Критический путь рассчитывается по длительностям, иерархии и связям «окончание-начало». Запас времени поглощает часть задержки; сдвиг даты проекта возникает после исчерпания резерва. Дни задержки всех работ не складываются механически.

Ответственный вводит в редакторе этапа verified_progress_percent (0..100), verified_progress_date и обязательное verified_progress_note: акт, замер объёмов и проверившее лицо. Дополнительно задаётся expected_finish_date. Дата замера проверяется с учётом переданного IANA часового пояса проекта; точность данных - календарный день. Будущий замер отклоняется.

| Основание | Результат |
|---|---|
| Датированный ручной замер 100% с основанием | Завершение подтверждено в дату замера |
| Неполный замер и ожидаемая дата ответственного | Сценарий по указанной ожидаемой дате |
| 0 < прогресс < 100, ожидаемая дата не задана | Сценарий сохранения среднего физического темпа от планового начала до замера |
| Нет пригодного физического замера | Плановый ориентир; физический прогресс неизвестен |

```text
elapsed_days = (measurement_date - planned_start_date) + 1
scenario_duration = ceil(elapsed_days * 100 / measured_percent)
scenario_finish = planned_start_date + scenario_duration - 1
```

Пример: начало 1 января, замер 5 января - 25%. При неизменном среднем темпе сценарий даёт 20 января. Если ответственный ожидает 18 января, используется его явная оценка. Сценарий не сдвигается ежедневно только из-за старения замера: нужен новый замер, а не автоматическое наращивание задержки.

Проверки техники без отклонений показывают ресурсное соответствие и не делятся в формулу физического темпа. Последний снимок с техникой не объявляет этап завершённым; истечение срока с давним отклонением не доказывает текущую просрочку. Без ручного подтверждения завершения просроченный плановый интервал обозначается как непроверенный.

Фотооценка готовности показывается отдельно от физических объёмов. Сценарная кривая объекта строится только при физических замерах всех листовых работ; используется явное взвешивание по плановой длительности. Это обзорная модель, не сметный процент готовности. При паузе история сохраняется, будущая дата сдачи и линия сценария отключены.

## 7. Руководство пользователя

Администратор создаёт объект, зоны, камеры и права участников. Участник работает только с назначенными объектами. Вход основан на сессии; отображение ссылки в интерфейсе не заменяет серверную проверку доступа.

1. Выберите объект. Проверьте адрес, статус и календарный план. Демонстрационные даты не следует смешивать с реальными отчётными данными.
2. Откройте камеру. Задайте источник снимка, дату и при необходимости точное время съёмки с часовым поясом. Время загрузки не подменяет время съёмки.
3. Разметьте кадр: рабочий участок, стоянка и другие назначения. Свяжите рабочий полигон с этапом. После смены ракурса проверьте применимость разметки.
4. В календарном плане проверьте начало, окончание, предшественников, обязательную и разрешённую технику. Укажите основание нормы. Красный критический путь показывает расчётную чувствительность срока.
5. Выполните анализ. Откройте рамки и план/факт. Проверьте исключённые объекты, неоднозначность классов, рабочую зону и доступную дату.
6. Откройте отклонение. Разделите видимое расхождение и независимые подтверждения; при необходимости получите новый кадр и уточните наличие ресурса у диспетчера.
7. Зафиксируйте решение, комментарий и результат контрольной проверки. Один кадр без расхождения не равен инженерной приёмке устранения.
8. Для сроков откройте редактор работы и внесите физическую готовность, дату и основание. При наличии укажите ожидаемое окончание. На странице прогноза проверьте тип сценария и влияние резерва. Карточки проекта и главная показывают только подтверждённый физический процент; без замера выводится «Нет замера» или прочерк, а не доля истёкшего времени.

Погода доступна в отдельной панели на 72 часа. Риск содержит параметр, период и технологическое условие; при недоступном источнике отсутствие данных не означает благоприятную погоду.

Коррекции распознавания сохраняются в центре обучения. Публикация кандидата выполняется осознанно администратором после проверки; накопленные коррекции не подтверждают автоматически улучшение на новых камерах. Android-клиент использует тот же API; фоновая push-доставка не считается реализованной только из-за наличия списка уведомлений.

## 8. Установка и воспроизводимость

Рекомендуемый путь - Docker Compose из корня репозитория. До сборки подготовьте models/yolov8s-worldv2.pt, локальные веса CLIP в weights/clip и исходные ресурсы, которые копирует Dockerfile. Сборка фронтенда и установка пакетов требуют доступных реестров либо заранее подготовленных зеркал / кэша. Не заявляется работа офлайн без подготовки зависимостей.

Создайте собственный .env на основе .env.example. Задайте секрет Django, пароли БД и создаваемых пользователей, доверенные хосты и origin. Для внешнего адреса настройте HTTPS и secure-cookie. Значения секретов в документацию и снимки экрана не включаются.

```text
cp .env.example .env
# Заполнить собственные значения, подготовить веса
docker compose build app admin
docker compose up -d db
docker compose run --rm --no-deps app python manage.py migrate --noinput
docker compose run --rm --no-deps app python manage.py createsuperuser
docker compose up -d
```

В PowerShell вместо cp допустимо Copy-Item. Опциональный сид демонстрационных справочников: docker compose exec admin python manage.py seed_demo_data. Сид не является загрузкой производственного графика. Новый реальный объект настраивается отдельно. app и admin привязаны к loopback-портам 8000 / 8001; внешнюю публикацию обеспечивает настроенный reverse proxy.

Проверка запуска: /api/health отвечает, вход работает, пользователь видит свой объект, открываются план и камера, анализ сохраняет наблюдение, файл доступен только по разрешённому проекту. После перезапуска сохраняются PostgreSQL, data/uploads и артефакты models; резервное копирование и восстановление проверяются отдельно.

## 9. Ограничения, доступ и эксплуатация

Видимость ограничена кадром: окклюзии, дальняя техника, темнота, перекрытия и смена ракурса ухудшают счёт. Нулевая детекция не равна доказанному отсутствию машин. Детектор допускает два одновременных обращения: одно выполняется, одно ожидает; сверх лимита API отвечает 503 с Retry-After: 5. Бесконечной очереди CPU-инференса нет. Неподтверждённая дата и неопределённое распределение общих ресурсов требуют проверки. Порог уверенности и согласованный профиль повторов не устраняют систематические ошибки класса.

Ресурсная норма должна иметь инженерное основание. Ошибка графика, неактуальная зона или неверная норма воспроизводимо создадут неверный сигнал даже при хорошем детекторе. Для утверждения о простое нужны фактические операции и технологический регламент; сравнение двух положений машины этого не заменяет.

Необязательное языковое обогащение работает отдельно от детерминированной проверки. Состояния ожидания, завершения, отключения и ошибки показывают доступность дополнения; основной анализ и доказательства сохраняются при недоступности языкового сервиса. Работает один обработчик и очередь до 8 ожидающих заданий; переполнение даёт явную ошибку дополнения. В БД сохраняются pending / disabled / complete / failed, queued_at и expires_at; ожидание старше часа при чтении показывается как ошибка. Очередь в памяти не восстанавливается после перезапуска. Отложенное языковое дополнение не изменяет жизненный цикл отклонений: решение опирается на синхронные правила и геометрию. Это не промышленный брокер заданий.

Доступ к объектам, наблюдениям и изображениям проверяется на сервере. Общедоступные руководство и презентация не должны содержать реальные секреты или частные снимки. История анализа и SHA-256 облегчают аудит, но не заменяют политику хранения, журнал административных изменений и проверенные резервные копии.

Локальная Qwen не интегрирована; существующий внешний языковой адаптер не считается закрытым контуром. Для изолированной установки дополнительно нужны локальные метеоданные, тайлы карты, подготовленные зависимости и сетевые испытания. Выбор квантования Qwen, расход памяти и задержка требуют отдельного стендового измерения.

Регистрация демонстрационной поставки использует заглушку почтового канала. Реальная отправка и подтверждение адреса требуют отдельной настройки. Capacitor-обёртка не гарантирует push-доставку. Погодный риск, фотооценка и сценарная дата должны сохранять собственные источники и не заменять факты строительного производства.

## 10. Демонстрация, проверка алгоритмов и состав сдачи

Демонстрацию проводят на отдельном тестовом объекте и разрешённых изображениях. Для временной серии нужны разные файлы с подтверждённым временем и подходящими интервалами; повтор загрузки одного файла не заменяет эксперимент.

| Шаг | Проверяемый результат | Доказательство |
|---|---|---|
| 1. План 6, видно 2 | План/факт 6 / 2, дефицит 4 только в рабочем участке | Рамки, зона, правило, исключённые объекты |
| 2. Машины на стоянке | Не увеличивают рабочий ресурс | Причина исключения каждой детекции |

## Коррекции · канбан Learning

Меню проекта → «Коррекции». Колонки: «К разбору», «В работе», «Готово к обучению», «На дообучении», «Обучено». Новые неоднозначные или низкоуверенные (<0,65) детекции создают задания автоматически. Исторические случаи собираются кнопкой «Найти спорные снимки»; любой доступный кадр можно добавить вручную. Это задания проверки, а не подтверждённые ошибки детектора.

«Взять и разметить» назначает исполнителя и открывает исходный кадр с рамками. Можно добавлять рамки протягиванием, выбирать объект, менять класс, отмечать «Не техника», уточнять координаты и удалять рамки. Черновик сохраняется на сервере. Для готовности необходимо принять решение по каждой рамке или явно подтвердить пустую сцену. Исходные наблюдения не переписываются; подготовленные фрагменты сохраняются отдельно. Изменения защищены ревизиями и правами исполнителя, соседние проекты изолированы.

Администратор выбирает готовые задания и запускает дообучение. Нужны минимум два разных класса (включая отрицательный «Не техника»). Работает существующая методика CLIP-признаков и логистического классификатора-корректора, а не переобучение всех весов YOLO-World. Очередь хранит точные идентификаторы заданий и коррекций; одновременно выполняется один запуск. Успех означает созданный файл модели и версию-кандидат, только после этого карточки становятся «Обучено». Ошибка возвращает задания в готовность с причиной. Ожидание более двух часов считается сбоем при следующей проверке доски.

Для проверки качества разделяются целые исходные снимки, включая повторные загрузки с одинаковой SHA-256. Если независимых наблюдений недостаточно для проверки всех классов, метрики явно недоступны. Факт обучения не означает доказанный прирост точности или автоматическую публикацию модели. Проектные кандидаты не могут активироваться как глобальная legacy-модель. Публикация и эксплуатационная валидация остаются отдельным решением администратора.

Карточки можно перетаскивать и упорядочивать кнопками «Выше/Ниже». На телефоне доска прокручивается внутри блока; переходы доступны через меню статуса. Обучающие статусы назначаются обработчиком, вручную объявить обучение завершённым нельзя.
