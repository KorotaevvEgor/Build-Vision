# BuildVision — сопроводительная документация

Формат: markdown как источник; при необходимости конвертируется в
`.doc`/`.pdf` перед финальной сдачей (см. требование раздела 7.2 ТЗ). **BuildVision** —
ребрендинг прототипа «СтройКонтроль»; техническое имя репозитория (`stroykontrol`)
не менялось — только отображаемое пользователю название.

## 1. Концепция

Снимок наблюдения + зона + дата → обнаруженная строительная техника →
сопоставление с активным этапом графика по настраиваемым правилам (Plan vs Fact по
количеству техники) → объяснимое предупреждение с доказательствами (исходный
снимок, рамки, применённое правило). Три исхода проверки: «Отклонений не
выявлено», «Возможное отклонение», «Недостаточно данных» — последний статус
осознанно используется вместо того, чтобы выдавать неуверенный
результат за установленный факт.

Поверх этого сквозного сценария продукт разбит на 6 модулей:

1. **Dashboard** — сводка (зоны/камеры/отклонения), текущий этап, баннер риска.
2. **AI Camera** — анализ снимка, Plan vs Fact по количеству, цепочка объяснения.
3. **Календарный план и Карта** — таймлайн этапов, карта с камерами по статусу зоны.
4. **AI Learning** — классификатор-корректор на коррекциях инженера.
5. **Прогноз сроков** — расчётный движок по темпу и погоде, без ML-предсказания.
6. **Мобильное приложение** — Capacitor-обёртка того же API для RuStore.

Поверх всего — сквозная **авторизация с двумя ролями** (Администратор/Участник
проекта) на базе сессий Django.

## 2. Архитектура

* **Backend:** FastAPI (Python), модульная структура:
  `detector.py` (YOLO-World + опциональный классификатор-корректор), `matching.py`
  (сопоставление с графиком по количеству), `forecast.py` (прогноз сроков),
  `learning.py`/`clip_embeddings.py` (AI Learning), `assistant.py` (ИИ-ассистент проекта,
  отвечает только на основе свежего среза фактов конкретного проекта), `auth.py` (сессионная авторизация), `insights.py`
  (агрегаты для Dashboard/Камер/Аналитики/Уведомлений), `weather.py`/`weather_matching.py`
  (погодные риски), `schedule.py`, `rules_config.py`, `vocabulary.py`, `weather_rules_config.py` —
  загрузка конфигурации из PostgreSQL через Django ORM (с файловым откатом), `persistence.py` —
  сохранение результатов анализа.
* **Админ-панель:** Django + Django admin (`core/`, `admin_panel/`) поверх той же
  PostgreSQL — единственный источник правды для справочников и место просмотра
  истории анализа. Запускается отдельным лёгким образом (`Dockerfile.admin`), без
  ML-зависимостей.
* **Авторизация:** сессии Django (`django.contrib.sessions`, та же таблица
  `django_session`, что и у admin) вместо отдельной JWT-системы — FastAPI уже делает
  `django.setup()` для чтения справочников. Две роли — Администратор и Участник проекта
  (`UserProfile.role`). Все эндпоинты, кроме `/api/health` и `/api/auth/*`, требуют валидную сессию.
* **Frontend:** React + TypeScript + Vite, тёмная индустриальная тема, 8 экранов
  (Главная, Камеры, Камера—AI-анализ, Карта, Календарный план, Прогноз, Центр
  обучения AI, Аналитика/Уведомления/Настройки), Leaflet для карты, собственная
  дизайн-система на CSS-переменных с едиными цветами по классам техники.
* **Мобильное приложение:** Capacitor-обёртка того же React-кода и API для RuStore
  (`mobile/`) — та же сессионная авторизация, новых backend-эндпоинтов не потребовалось.
* **Развёртывание:** `docker-compose.yml` с тремя сервисами — `db` (PostgreSQL),
  `app` (FastAPI + модель + собранный фронтенд на одном адресе), `admin` (Django admin).

## 3. Модель данных и хранение

Все сущности хранятся в **PostgreSQL** через Django ORM (`core/models.py`) и
редактируются через Django admin (`http://.../admin/`). FastAPI использует
ту же БД напрямую через ORM (`backend/app/django_bridge.py`), без промежуточного
REST/HTTP-слоя до Django.

| Сущность (Django-модель) | Назначение | Ключевые поля |
|---|---|---|
| ConstructionSite | Площадка | name, note, is_demo, boundary_geojson |
| Zone | Зона | site, external_id, name, geometry_geojson |
| Camera | Камера, привязанная к зоне | zone, external_id, name, latitude, longitude, is_demo |
| VocabularyClass | Класс техники словаря | key, label_ru, prompts[], in_taxonomy |
| Stage | Этап графика | external_id, zone, work_code, work_name, start/end_date |
| StageRule | Правило техники этапа | stage, required (M2M через StageRequiredItem), allowed (M2M), alternatives_note |
| StageRequiredItem | Обязательная техника с количеством (Plan) | stage_rule, vocabulary_class, min_quantity |
| ConfusablePair | Известная путаемая пара классов | class_a, class_b, evidence_note |
| KnownLimitation | Измеренное ограничение качества | vocabulary_class, issue, description |
| WeatherRule | Погодное правило риска | stage, factor, comparison, threshold, units, message |
| MatchingSettings | Глобальные настройки (singleton) | ambiguity_margin |
| UserProfile | Роль и должность пользователя | user (1:1 auth.User), role (admin/participant), position |
| **Observation** | **Результат анализа одного снимка** | id (UUID), zone, image_path/sha256, observed_date, overall_status |
| Detection | Обнаруженная рамка | observation, class_key, confidence, bbox, ambiguous |
| StageEvaluationRecord | Результат проверки этапа в наблюдении | observation, stage, status, explanation, quantity_checks_snapshot, missing_required |
| WeatherRiskRecord | История погодных рисков | stage, factor, peak_value, start/end_time_utc |
| Correction | Коррекция инженера по одной детекции (AI Learning) | observation, crop_image_path, original_class_key, corrected_class, created_by |
| ModelVersion | Версия классификатора-корректора | version_label, status (candidate/production/archived), metrics_json, artifact_path |

**Источник данных и откат.** Исходные YAML/JSON/GeoJSON в `data/config/`
используются для однократного сида БД (`python manage.py seed_demo_data`,
идемпотентно) и как резервный откат, если Postgres временно недоступен
(`backend/app/django_bridge.py`). После сида источником правды является БД —
изменения через Django admin видны в API сразу, без перезапуска FastAPI
(конфигурация читается заново на каждый запрос).

**Проверено:** `scripts/verify_db_persistence.py` подтверждает, что загрузчики
действительно читают из БД (файлы временно отключаются) и что цикл
сохранение→чтение через `persistence.py` работает корректно внутри Docker-сети.

## 4. Таксономия техники (8 классов)

Самосвал, экскаватор, каток, кран-манипулятор, автобетоносмеситель,
бульдозер, грузовик, автокран. Определены в `data/config/vocabulary.yaml`
как текстовые промпты для YOLO-World (открытый словарь, без дообучения).

Известные ограничения качества по классам — в
[`detector_quality_report.md`](detector_quality_report.md). Кратко:
экскаватор/каток иногда путаются с краном-манипулятором (обрабатывается
через `confusable_class_pairs` → статус «Недостаточно данных»); класс
«Самосвал» имеет низкую точность на этом датасете (систематические
ложные срабатывания на фоне); «Автобетоносмеситель» — низкая полнота.

## 5. Этапы графика в демо-сценарии

Три этапа, привязанные к реальным кодам справочника заказчика
(`works_catalog.csv`), с демонстрационными датами и предположениями о
технологии (полный список — `demo_schedule.json`):

1. **Устройство котлована** (код 12.3.1.) — экскаватор + самосвал.
2. **Устройство бетонной подготовки** (дочерняя работа кода 12.3.4.) —
   автобетоносмеситель.
3. **Уплотнение грунта** (дочерняя работа кода 12.3.7.) — каток.

## 7. Честность и объяснимость (как это реализовано)

* Каждое предупреждение показывает: этап, зону, дату, ожидаемое и
  обнаруженное (с числами Plan vs Fact), применённое правило, рамки-доказательства на исходном
  снимке.
* Без подтверждённой даты снимка результат всегда «Недостаточно данных»
  (`matching.py`), а не молчаливое использование текущей даты.
* Неоднозначные классификации (известные confusable-пары) не выдаются за
  надёжный ответ — статус «Недостаточно данных» с пояснением; классификатор-корректор
  (модуль AI Learning) может уточнить класс, но не снимает флаг `ambiguous` автоматически.
* Погодные предупреждения и прогноз сроков визуально отделены от предупреждений по
  снимкам и явно помечены как прогноз, а не наблюдаемый факт; при
  недоступности API — честный статус «unavailable», а не «рисков нет».
* **AI Learning — честная валидация.** В датасете нет размеченного held-out набора (только
  разбиение файлов на dev/val/holdout без разметки классов, см. `data/config/splits.json`), поэтому
  метрики классификатора-корректора (`scripts/train_correction_classifier.py`) честно измеряются
  train/test-разбиением внутри самих накопленных коррекций инженера — и при недостатке данных честно
  помечает валидацию недоступной, а не заменяет выдуманным числом. Кандидат становится рабочей
  версией только вручную (`POST /api/model-versions/{id}/deploy`), не автоматически после обучения.
* **Прогноз сроков — честная эвристика.** «% выполнения»/темп — не физический прогресс, а
  доля подтверждённых наблюдений без отклонений (`forecast.py`); погода учитывается только в
  реальном горизонте Open-Meteo (~72ч), без выдумывания риска на более дальние даты.
* Демонстрационные данные (координаты площадки, график, даты) везде
  явно помечены `is_demo`/`location_is_demo` и подписаны в интерфейсе.

## 8. Ограничения и направления развития

**Известное ограничение среды (не продукта).** На машине разработки
прямое подключение с Windows-хоста к Postgres/HTTP через проброшенные порты
Docker Desktop (127.0.0.1) было нестабильным: TCP-соединение устанавливается, но
данные приложения повреждаются (воспроизведено и для Postgres, и для простого HTTP).
Внутри сети Docker (`docker compose exec`/`docker run --network ...`) всё
работает корректно — это и было использовано для проверки
(`scripts/verify_db_persistence.py`). **Подтверждено после деплоя:** на реальном
Linux-сервере (Ubuntu 24.04, арендованный VPS) этого слоя Docker Desktop нет,
ограничение не воспроизвелось: прямое подключение к Postgres через 127.0.0.1
и сквозной анализ снимка через API/nginx работают без проблем.

**Особенности, обнаруженные при деплое на VPS** (исправлены в репозитории,
подробнее в README, раздел «Продакшн-развёртывание (VPS)»):

* `opencv-python` (зависимость `ultralytics`) требует системные библиотеки в
  образе, отсутствующие в `python:3.13-slim` по умолчанию (`libgl1`,
  `libglib2.0-0`, `libxcb1` и др.) — без них импорт `cv2` падает уже при
  первом вызове детектора.
* Пакет `clip` не публикуется на PyPI и требует установки из git во время
  сборки образа (`ultralytics/CLIP`) — требует установленного `git` в образе.
* На использованном VPS без глобального IPv6-адреса Docker/BuildKit всё равно
  пытался резолвить registry по IPv6, что ломало `docker compose build`.
  Помогло только полное отключение IPv6 на уровне ядра через
  `ipv6.disable=1` в GRUB и ребут; частичные фиксы (`daemon.json`, `sysctl`)
  были недостаточны.

**Не реализовано в этом цикле:**

* Реальные камеры с настоящим видеопотоком — в датасете только 100 статичных снимков; «LIVE»
  на экране камеры — это последний реально сохранённый анализ, а не поток.
* Автоматическое OCR-извлечение выжженной в кадре даты (сейчас дата
  вносится вручную/с ручным подтверждением; ~85% снимков датасета имеют
  подходящий для этого штамп — см. переписку по итогам аудита).
* Полное дообучение самого детектора YOLO-World на собственной разметке — вместо этого
  реализован лёгкий классификатор-корректор на CLIP-эмбеддингах (модуль AI Learning) —
  полное дообучение на CPU нереалистично по времени.
* Редактор полигонов зон прямо в интерфейсе (сейчас — загрузка готового
  GeoJSON через Django admin).
* ML-модель прогноза (нейросеть, предсказывающая срок) — вместо неё расчётный движок на
  реальных метриках (см. модуль «Прогноз сроков»); полноценное ML-предсказание потребовало бы
  историю задержек по множеству объектов, которой нет.
* Ограничение частоты попыток входа и восстановление пароля для веб/мобильной авторизации
  (авторизация с двумя ролями уже реализована, но эти две части вне охвата).
* Push-уведомления в вебе/мобильном приложении — нет инфраструктуры доставки, список
  уведомлений тянется при открытии экрана/приложения.

## 9. Рекомендации по камерам наблюдения

Для повышения качества автоматической проверки в реальном внедрении:

* Фиксированный ракурс на протяжении всего этапа, с привязкой к
  конкретной зоне (перемещение камеры должно обновлять привязку).
* Обзор, охватывающий место работ и подъездные пути — иначе «отсутствие»
  техники может быть просто следствием того, что она вне кадра.
* Минимизация перекрытий техники друг другом или объектами площадки.
* Достаточный размер техники в кадре (не мелкий дальний план) — точность
  классификации быстро падает на мелких объектах.
* Достаточное освещение в тёмное время суток и в пасмурную погоду.
* Синхронизация времени камеры/сервера, чтобы штамп даты (если есть)
  соответствовал реальному времени съёмки.
* Актуализация привязки зоны после любого перемещения или переустановки
  камеры.

Конкретные числовые требования к высоте установки, углу обзора и
разрешению матрицы не приводятся — они требуют обследования реальной
площадки, которого не проводилось.
